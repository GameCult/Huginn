### 2.2 The `question` and `ruling` schemas and admission rules

Leaf definitions, `F:\Projects\Huginn\crates\eureka-pipeline\src\lib.rs`, Huginn `0b3cac3`:
- `PipelineQuestion` (lib.rs:634-636): `campaign: Slug`, `label: Label` (`[A-Za-z0-9_-]{1,64}`), `title: Title`, `question: Para` (<= 4000 bytes), `options: Vec<QuestionOption>` (max 8), `recommended: Label`, `depends: Vec<Line>` (max 8, Line <= 1000 bytes), `raised_in: Option<PipelineRef>`, `asked_on: Date`. `QuestionOption { label: Label, text: Line }` (lib.rs:585). There is no field for a presenter, Persona, `lean`, `flag` or display order; the campaign slug is the only domain key on the document. `eureka-state` query headers return `options` as labels only; `view` returns the full document.
- `PipelineRuling` (lib.rs:637-639): `campaign`, `label`, `title`, `answers: Option<Short>` (question id), `choice: Option<Label>`, `ruling: Para` (<= 4000 bytes), `operator_quote: Option<Para>`, `ruled_on: Date`, `precedents: Vec<ForeignRef>` (max 8), `authority: RulingAuthority { Operator, Standing, Defaulted, Mind }` (lib.rs:567).
- Admission rules, `crates/huginn-mind/src/admission.rs`:
  - Question: needs >= 2 options and `recommended` equal to one option label, else `InvalidOptions` (admission.rs:462-465); option labels unique.
  - Ruling: `operator_quote` present with an authority other than `Operator` is refused `QuoteWithoutOperator` (admission.rs:468-470). If `answers` is present, the question must exist (`MissingReference`), be in force or resolved only by this ruling (`AlreadyResolved`), and `choice` must equal one option label, else `InvalidChoice` (admission.rs:471-485; the missing-choice case compares `""` to the labels, so `choice: None` with `answers` set is refused too). Test pins at admission.rs:1899-1905 (choice "C" refused, "A" admitted).
  - A ruling with `answers: None` is admitted with no check of the above and derives no resolution, so it does not close any question (`derive`, admission.rs:385-405: only `Ruling` with `answers` derives a `Resolution::Answered`; the resolution copies the ruling text as rationale and its `ruled_on`).
  - Where an answer falls outside the options: the leaf has no free-form choice path. A free-text answer can ride in `ruling` text and `operator_quote` of a ruling, either with `answers` (then `choice` must still be an option label) or without `answers` (then nothing resolves the question; a withdrawal or supersession resolution is separate). The artifact desks carry free text in the `note` field of `answers/<docId>`, which Self copies into the ruling by hand.
  - Resolutions of a ruling are by withdrawal only (admission.rs:682-684); memory note `observation-is-not-a-ruling.md` records "rulings cannot be withdrawn" and are superseded by a new Operator ruling quoting her correction.
  - Replay: an exact replay answers `AlreadyAdmitted` with the first receipt (admission.rs header comment A9).
- Query facts for an "open questions" read: the selection supports `schemas`, `fields` predicates, `in_force` alias (query.rs:520-523 "`in_force` is the caller's to ask for and the mind's to derive"), `cites`/`cited`, cursor paging (limit clamped 1..200), and an optional `semantic` rank (not cursor-paged; refused `Unavailable` when the index is failing). A `Question` header carries `status` `InForce` or `Resolved{outcome, resolution}`; observed outcomes: `Answered{by}`, `Withdrawn{reason}`, `Superseded{by}`, `Recorded{reason}`, `Deferred{to}`, `Fixed{by,commit}`.
- Persona state: `huginn-mind/src/persona.rs` stores one `gamecult.persona_state.v0` per mind, schema-validated, replaced whole under CAS with a receipt (cut `eureka-substrate:cut_spec:cut-huginn-persona-state.r3`, InForce 2026-10-09). `HuginnClient` has persona methods per the cut title.

## 3. Prior art: a human rules on decisions an agent raised

All web pages accessed 2026-10-20.

### 3.1 Decision records

- adr-tools (https://github.com/npryce/adr-tools): numbered Markdown ADRs in `doc/adr` by default; `adr new -s 9 <title>` creates an ADR that supersedes ADR 9 and updates ADR 9's status; statuses and template fields are not listed on that page.
- Log4brains (https://github.com/thomvaill/log4brains): ADRs as Markdown in the git repo, published as a static site (`log4brains build`, local `log4brains preview` with hot reload); statuses given as proposed, accepted, deprecated, superseded; an ADR is otherwise immutable, only its status changes; metadata guessed from raw text and git logs (CI needs full history); default template MADR; planned features include a decision backlog and ADR editing from the UI.
- MADR (https://adr.github.io/madr/): sections Context and Problem Statement, Decision Drivers, Considered Options, Decision Outcome (chosen option and justification), Consequences, Confirmation (how compliance is verified), Pros and Cons of the Options, More Information; optional front matter `status`, `date`, `decision-makers`, `consulted`, `informed`; statuses proposed, rejected, accepted, deprecated, "superseded by" another ADR.
- In-house equivalent: mind `question` (context, options, recommended, depends, raised_in) -> `ruling` (authority, quote, precedents) -> derived `Resolution` (`Answered`, `Superseded`, `Withdrawn`); records are typed documents with receipts, not files (Huginn `README.md` Authority section).

### 3.2 Review and approval queues

- GitHub pull request reviews (https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/reviewing-changes-in-pull-requests/about-pull-request-reviews): three review states (Comment, Approve, Request changes); administrators can require approvals before merge via protected branches; CODEOWNERS auto-requests review from owners of changed code. The fetched page does not cover stale-review dismissal or the review-to-commit tie.
- Gerrit (https://gerrit-review.googlesource.com/Documentation/config-labels.html): label votes (Code-Review -2..+2, Verified -1..+1); -2 blocks submit, +2 enables it; submit requirements define submittability; votes are tied to a patch set, and on a new patch set a vote is copied forward only if it matches the label's `copyCondition` (for example `changekind:NO_CODE_CHANGE`, `changekind:TRIVIAL_REBASE`); non-copied votes become "outdated", the uploader is notified and the voter is added to the attention set.
- Linear Triage (https://linear.app/docs/triage): an inbox for issues from integrations or outside the team; actions Accept (to default status, optional comment), Decline (Canceled, optional explanation), Mark as duplicate (merge into an existing issue), Snooze (hidden until a chosen time or new activity); triage responsibility can rotate by on-call schedule (Business and Enterprise plans); the page does not describe automatic decline or snooze.

### 3.3 Agent harnesses with a human approval step

- LangGraph `interrupt()` (https://docs.langchain.com/oss/python/langgraph/interrupts): saves graph state through a checkpointer, returns a JSON-serializable payload to the caller (`__interrupt__` or `stream.interrupts`); resume with `Command(resume=...)` on the same `thread_id`; the node restarts from its beginning on resume, so code before `interrupt()` must be idempotent; interrupts must be called in the same order each time; patterns: approve or reject, review and edit, tool interrupts (approve, edit arguments, cancel), input validation by re-entering the node, parallel interrupts keyed by interrupt id; optional response schema validates resume values (`langgraph>=1.2.12`). (An older URL, langchain-ai.github.io/langgraph/concepts/human_in_the_loop/, returned only a redirect.)
- OpenHands confirmation mode (https://docs.openhands.dev/sdk/guides/security): policies `AlwaysConfirm`, `NeverConfirm`, `ConfirmRisky(threshold)`; pending actions put the conversation in `WAITING_FOR_CONFIRMATION`; approve by `conversation.run()`, reject by `conversation.reject_pending_actions("reason")` with the reason returned to the agent; an LLM security analyzer rates actions LOW/MEDIUM/HIGH/UNKNOWN; `conversation.execute_tool()` bypasses both analyzer and policy.
- OpenAI Agents SDK human-in-the-loop (https://openai.github.io/openai-agents-python/human_in_the_loop/): `needs_approval` (bool or async callable per call); a paused run exposes `result.interruptions` (`ToolApprovalItem`: agent, tool, arguments); `result.to_state()` serializes (`to_json`/`to_string`); `state.approve(interruption)` or `state.reject(interruption, rejection_message=...)` per call, sticky with `always_approve`/`always_reject`; resume with `Runner.run(agent, state)`; docs state serialized state is not authenticated, so reviewer identity and authorization must be verified before resuming.
- Claude Agent SDK (https://code.claude.com/docs/en/agent-sdk/user-input): `canUseTool` fires for tool approval and for `AskUserQuestion`; callback may stay pending indefinitely, or a `PreToolUse` hook `defer` decision lets the process exit and resume from the persisted session; responses: allow (optionally `updatedInput`), allow with `updatedPermissions` (approve and remember), deny with a message the agent sees; `AskUserQuestion` input is 1-4 questions with 2-4 options each (`question`, `header` <= 12 chars, `options[{label, description, preview?}]`, `multiSelect`), the answer is a map from question text to chosen label (arrays or comma-joined for multi-select), free text goes in the answer value, optional `response` for a general reply; options may carry an HTML preview (`previewFormat: "html"`); not available in subagents; `PermissionRequest` hook can notify Slack, email or push.
- Claude Code permission modes (https://code.claude.com/docs/en/permission-modes): `default` (prompts for edits, shell, network), `acceptEdits`, `plan` (edits blocked until a plan is approved), `auto` (classifier reviews actions, ask rules still prompt), `dontAsk` (would-prompt calls are denied), `bypassPermissions`.
- HumanLayer (https://github.com/humanlayer/humanlayer): the repo page states "the code here is pretty much all deprecated" and points to a rebuild at humanlayer.com; topics human-in-the-loop, claude-code; 11.7k stars. The approval API (`require_approval`, `human_as_tool`) was not shown on the fetched page; not established here.
- Other Claude-side precedent in this environment: Claude Code `AskUserQuestion` (as used by Self in this session family, memory `forks-for-understanding.md`: "one AskUserQuestion per fork") is the question channel the desks replaced for open forks.

### 3.4 Known failure modes (sourced)

- Approval fatigue and rubber-stamping: Anthropic engineering post (https://www.anthropic.com/engineering/claude-code-auto-mode): "approval fatigue, where people stop paying close attention to what they're approving"; users approve 93% of permission prompts.
- Automation bias and explanation limits: Green, "The Flaws of Policies Requiring Human Oversight of Government Algorithms" (Computer Law & Security Review 2022; https://arxiv.org/abs/2109.05067): surveys 41 policies; reports that most research finds people cannot reliably oversee algorithms, that people defer to automated tools and increase attention to the factors an algorithm emphasizes, and that explanations and transparency do not reliably improve oversight. EU AI Act Article 14(4)(b) (https://artificialintelligenceact.eu/article/14/): overseers must remain aware of the possible tendency to over-rely on system output (automation bias), notably where the system provides recommendations.
- Questions without context: Claude Code and SDK question forms bound questions to 1-4 per call and 2-4 options with a short label (`header` <= 12 chars); in-house record: the operator asked to understand each decision ("My decisions are the only reason anything gets done", 2026-09-29, `forks-for-understanding.md`), and a handoff one-liner lost "options and decision context" (operator, 2026-10-03, same note: "I want options and decision context to survive next time.").
