## 1. Opaque / reasoning state a caller must replay

### 1a. Anthropic Messages API
Pointers: T = https://platform.claude.com/docs/en/build-with-claude/thinking ; TS = .../thinking-troubleshooting ; P = .../preserved-thinking (linked from T, NOT fetched)

- Thinking arrives as `thinking` content blocks (fields `thinking`, `signature`) and `redacted_thinking` blocks (field `data`, opaque, encrypted). [T "Thinking encryption", "Redacted thinking blocks"]
- `signature` holds the full encrypted thinking; API uses it to verify blocks were generated by Claude; opaque, "don't interpret or parse". Streaming: arrives as `signature_delta` in a `content_block_delta` just before `content_block_stop`. [T "Thinking encryption"]
- `display: "omitted"` (default on newer models) returns thinking blocks with empty `thinking` string and populated `signature`; such a block is complete and must be replayed; text put into the empty field is ignored not rejected. [TS "The thinking field is empty"; T "Preserving thinking blocks" Note]
- Replay rules [T "Thinking with tool use", "Preserving thinking blocks"]:
  - Required: within a tool-use turn, pass thinking blocks back, complete and unmodified, with the `tool_use` block they accompanied.
  - Recommended: across turns pass everything back. Allowed: outside tool use, omit prior turns' thinking.
  - A tool-use loop is one assistant turn. Consecutive thinking blocks in the latest assistant message must match what the model generated: no reorder, edit, partial drop; includes `redacted_thinking`.
  - Filtering by `block.type == "thinking"` silently drops `redacted_thinking` and breaks the protocol. [T "Redacted thinking blocks" Tip]
- Errors [TS]:
  - Modified/dropped in latest assistant message: 400 `invalid_request_error`, message contains "`thinking` or `redacted_thinking` blocks in the latest assistant message cannot be modified".
  - Signature present but fails verify (truncated/altered/empty): 400 "Invalid `signature` in `thinking` block" (ends there; no prefix clause).
  - Fable 5.1, Opus 5.5, Sonnet 5.5, Haiku 5.5: replayed block valid only while `system`, `tools` and preceding messages are unchanged ("prefix check"): 400 "...The block is bound to a different conversation. Remove the block, or set `thinking.block_binding.prefix_mismatch_behavior` to "drop_block"." Enforced by default for accounts created on/after 2026-08-31; older accounts only when the request sets that field. Option needs beta header `thinking-binding-controls-2026-08-01`; response then carries an `input_transformations` array listing dropped blocks. [T "Preserved thinking"; TS]
  - Mid-turn toggle of thinking: no error; API silently disables thinking for that request and may strip blocks. [T "Thinking with tool use"]
  - Manual mode (`type:"enabled"`): final assistant turn must start with a thinking block; `type:"enabled"` is 400 on 4.7+ models. [extended-thinking page "Turn structure in manual mode"; TS table]
- Earlier-turn thinking stripped or kept: per model. Keep all prior turns: Opus 4.5+, Sonnet 4.6+, Haiku 5.5, Fable/Mythos 5/5.1. Keep last turn only: earlier Opus/Sonnet and Haiku through 4.5; API strips automatically on pass-back. Kept blocks bill as input. Override: `clear_thinking_20251015` context-editing strategy. [T "Thinking block preservation by model", "Preserving thinking blocks"]
- Portability:
  - Across platforms: `signature` values are compatible across Claude API, Bedrock, Google Cloud (Google managed); exception: Sonnet 5.5 and Haiku 5.5 blocks work only in the producing account or a linked account. [T "Thinking encryption"; P#account-bound-thinking not fetched]
  - Across models: "readable only by the model that produced it and certain other models"; API drops unreadable blocks without error and without billing. Fable 5.1 reads Opus 5 and (Claude API) Opus 5.5 blocks; Opus 5/5.5 do NOT read Fable 5.1 blocks; Fable 5.1 and Mythos 5.1 read each other only. Switching to them keeps reasoning; away from them drops it. [T "Thinking block preservation by model: Switching models", "Preserved thinking"]
- Prompt caching [T "Thinking and prompt caching"]:
  - Thinking config and resolved effort are rendered into the prompt; changing mode, `budget_tokens` or effort invalidates message-level breakpoints (and may invalidate tool/system ones).
  - Thinking blocks in a tool loop are cached automatically with tool results and count as input when read from cache.
  - Last-turn-only models: after a non-tool-result user message, earlier thinking is stripped from context/cache.
  - 1-hour cache suggested for long thinking sessions.
- Billing: thinking tokens billed as output; `usage.output_tokens_details.thinking_tokens` reports them (final `message_delta` when streaming). [extended-thinking page "Budget rules and tuning"]

Stop reasons (https://platform.claude.com/docs/en/build-with-claude/handling-stop-reasons, first 100k chars read):
- `end_turn`, `max_tokens`, `stop_sequence`, `tool_use`, `pause_turn` (server-tool loop hit iteration limit, default 10; resend assistant content to continue), `refusal` (HTTP 200, `stop_details` names policy category, null for other reasons), `model_context_window_exceeded` (treat as truncated).
- Streaming: `stop_reason` is null in `message_start`, appears in `message_delta`. `max_tokens` can end in an incomplete `tool_use` block.

Usage object (https://platform.claude.com/docs/en/build-with-claude/prompt-caching "Usage fields"):
- `input_tokens` = tokens after last cache breakpoint (uncached); `cache_creation_input_tokens` = 5m + 1h writes; `cache_read_input_tokens`; `cache_creation{ephemeral_5m_input_tokens, ephemeral_1h_input_tokens}`; `output_tokens`. total_input = cache_read + cache_creation + input_tokens.
- `output_tokens_details.thinking_tokens` (above). `server_tool_use` and `service_tier` fields: only seen via fetch-tool general-knowledge answer, API reference page was truncated before the schema: UNVERIFIED against docs. Token counts depend on tokenizer: Claude 4.7+ models (incl. Fable/Mythos 5/5.1) count ~30% more tokens for the same text. [token-counting page "Supported models", "Token counts on Claude Fable and Claude Mythos models"]
- Min cacheable prompt: 512 (Fable/Mythos/Opus 5.5/Opus 5/Sonnet 5.5/Haiku 5.5), 1024 (Opus 4.8, Sonnet 5/4.6/4.5), 2048 (Opus 4.7, Mythos Preview), 4096 (Opus 4.6/4.5, Haiku 4.5). Lookback 20 block positions. [prompt-caching page]

### 1b. OpenAI Responses API
Pointer: https://developers.openai.com/api/docs/guides/reasoning (via fetch summary)
- Reasoning items appear in `output`; opaque, no reasoning text returned (optional `summary`). Example item id prefix `rs_`; page gives no other id rules.
- Stateless mode (`store:false` or ZDR org): reasoning items include `encrypted_content` by default; `include: ["reasoning.encrypted_content"]` still accepted as legacy/no-op.
- Replay: stored -> `previous_response_id`. Manual -> pass prior output items. Function calling: pass back reasoning items returned with the last function call plus outputs; with several calls in a row, pass back all reasoning, call and output items since last user message. `all_turns` with `store:false`: keep every output item (encrypted reasoning, assistant `phase`) and replay full history. `reasoning.context` in the response reports effective mode (`current_turn`/`all_turns`).
- Other models: reusable only within the same model family; switching families, API omits incompatible reasoning even with `all_turns` (GPT-5.6 Sol/Terra/Luna interchange, not GPT-5.5).
- Usage: `usage.output_tokens_details.reasoning_tokens`, `usage.input_tokens_details.cached_tokens`; reasoning billed as output.

## 3. Wire choice for a typed local RPC

### 3a. MCP (spec revision 2026-07-28 is "latest" at fetch)
- JSON-RPC 2.0, UTF-8. Standard transports: stdio (newline-delimited) and Streamable HTTP (POST per message; JSON or request-scoped SSE reply). https://modelcontextprotocol.io/specification/latest/basic/transports
- Custom transports allowed; those over reliable byte streams (Unix sockets, TCP) "SHOULD reuse the stdio framing" (same page).
- Versioning: latest revision has NO initialize handshake; every request carries protocol version in `_meta.io.modelcontextprotocol/*` (HTTP also `MCP-Protocol-Version` header); unsupported -> error -32022 with `data{supported[], requested}`; client retries; `server/discover` MUST be implemented. Legacy (<= 2025-11-25) used `initialize` negotiation. Dual-era servers MAY serve both on one endpoint, selecting by how the client opens (modern `_meta` vs `initialize`). https://modelcontextprotocol.io/specification/latest/basic/lifecycle (rendered as "Versioning and Compatibility")
- Binary: base64 strings paired with `mimeType` (`ImageContent.data`, `AudioContent.data`, `BlobResourceContents.blob`).
- Error codes: -32700, -32600, -32601, -32602, -32603 (JSON-RPC); -32020 HEADER_MISMATCH, -32021 MISSING_REQUIRED_CLIENT_CAPABILITY, -32022 UNSUPPORTED_PROTOCOL_VERSION. https://modelcontextprotocol.io/specification/2026-07-28/schema

### 3b. gRPC / protobuf (https://protobuf.dev/programming-guides/proto3/)
- Unknown fields preserved on parse and re-serialized (lost when going through JSON or field-by-field copy). Never reuse field numbers; reserve removed numbers/names. Adding fields, removing (no reuse), adding enum values are wire-safe; changing a field number or moving a field into an existing oneof is not. Unknown enum values preserved (open enums store int; closed enums, e.g. Java, special-case).
- `bytes`: arbitrary byte sequence (length limit garbled in fetch).
- `package` prevents name clashes; page does NOT frame packages as a versioning mechanism ("versioning by package names" claim: UNVERIFIED on this page).

### 3c. MessagePack / rmp-serde
- msgpack spec: bin 8/16/32 = 0xc4/0xc5/0xc6 with 8/16/32-bit BE length; str family separate (0xd9-0xdb, fixstr 0xa0-0xbf); ext 0xc7-0xc9 and fixext 0xd4-0xd8, app ext types 0-127, -1 = Timestamp; array 0x90-0x9f/0xdc/0xdd; map 0x80-0x8f/0xde/0xdf. Spec recommends deserializers accept bin and str8 in minor releases, serializers distinguish in major. https://github.com/msgpack/msgpack/blob/master/spec.md
- rmp-serde: serde derive treats `Vec<u8>` as an array of values (about 50% overhead per docs); wrap with `serde_bytes` or use `Serializer::with_bytes` to emit bin. Re-exports `to_vec` and `to_vec_named` (the page does not explain the struct encoding difference; array-vs-map: UNVERIFIED here). Unknown-field handling not covered. https://docs.rs/rmp-serde/latest/rmp_serde/
- Cap'n Proto: not searched. UNVERIFIED.

### 3d. Keeping two wire versions alive
- MCP dual-era server (3a): one endpoint serves both generations; discriminator is how the first message opens (per-request `_meta` vs `initialize`); client probes `server/discover` (stdio) or attempts modern request and inspects 400 body (HTTP) and caches the result per server process/origin; a modern-only server SHOULD name its supported versions in the error it returns to `initialize`; compatibility matrix in the versioning page.
- Protobuf field-number discipline (3b).
- Version byte / frame tag, side-by-side schema ids, generic dual-stack guidance: no source fetched. UNVERIFIED.

## 4. Probes (Imagination, Yggdrasil ygg-verify rust image, 2026-10-28)

Scratch clone of ModelConnector at `ec0519d` plus a probe-only commit (never pushed to the
forge). Baseline: `cargo test --workspace` and `--features model-connector/daemon` green, 77
tests passed in all.

- P2 Decoding the real v2 frame `tests/fixtures/wire_v2/envelope_invocation.mp` (the bytes
  CodexConnector `fd7cec4` produced): 735-byte frame for 429 bytes of ciphertext (209 of them
  >= 128), ratio 1.713. First byte `0x96`: a positional six-element array. It decrypts under
  `parity-distinct-test-key` to caller `parity-caller`, request `request-1`, model `gpt-5.4`,
  4 input items, 1 tool, schema `gamecult.codex.transport_invocation.v2`.
- P2 The same envelope with the ciphertext as MessagePack `bin` (`serde_bytes`): 526 bytes,
  ratio 1.226 (the rest is ids and nonce). A 1 MiB all-high ciphertext: v2 frame 2,097,251
  bytes, bin frame 1,048,675; the kit's `frame_bytes_for_payload(1 MiB)` = 2,097,750.
- P2 The v2 `TransportEnvelope` type decodes a bin-encoded ciphertext and compares equal
  (rmp-serde reads bin into `Vec<u8>`). Encoding is the only change bin needs.
- P3 `ProviderRequest` positional 267 bytes (`0xdc` array16), named (`to_vec_named`) 590
  bytes (`0xde` map16). The v2 type decodes the named encoding and compares equal.
- P4a A struct with one added field: positional encoding fails to decode in the old type
  ("array had incorrect length, expected 3"); named encoding decodes with the field ignored.
  So positional MessagePack cannot add a field without breaking every reader, and named
  encoding drops unknown fields silently unless the type denies them.
- P4b A v2 `InputItem` decoding a `ReasoningState` variant fails: "unknown variant". A v2
  peer cannot read a v3 transcript at all; there is no partial compatibility to preserve.
- P5 A v3 envelope schema id under v2 `decrypt_invocation`: `Err(Envelope)`, before any
  decryption. A v2 daemon given a v3 envelope drops the connection; it never answers.
- PC CultNet carriage. `CultNetMessage::OperationRequest` (cultnet-rs at CultLib `a4eae90`)
  carrying the sealed envelope (named, bin ciphertext, ids at 256 bytes) as its
  `messagepack-base64` payload, encoded with `encode_cultnet_message_to_vec(..,
  CultNetSchemaV0)` and decoded back, round-trips equal. Frame over ciphertext: 4.45 at 429
  bytes (fixed overhead), 1.354 at 64 KiB, 1.335 at 1 MiB, 1.334 at 8 MiB; encode 6.5 ms and
  decode 1.0 ms at 1 MiB (release). The worst case is deterministic (base64 is exactly
  4*ceil(n/3)), where v2's integer array is up to 2.0x and depends on the bytes.

  messages (`contracts.rs:780`): CultNet has no binary operation payload today.
- CultNet's security options hold one connection key per server (`security.rs:51-75`); the
  kit binds one key and epoch per caller and seals ids into the AES-GCM AAD
  (`service.rs:19-65`, `envelope.rs:245-253`).
- Huginn already speaks this shape: `huginn-mind/src/envelope.rs` carries named MessagePack
  as base64 in `cultnet.operation_request.v0`, checks `service_id`, `payload_schema` and the
  operation against the decoded payload, and publishes its JSON Schema with `schemars`.

## 5. What the cut takes from this

- Reasoning item granularity follows the providers: Anthropic requires the latest assistant
  turn's thinking blocks complete, unmodified and in place beside their `tool_use`; OpenRouter
  carries `reasoning_details` per block with an index. So one `ReasoningState` item per
  provider block, in transcript order, holding the connector's encoding of the whole block
  (Anthropic: `thinking` text and `signature`, or `redacted_thinking` data, since a summarized
  block must come back with both).
- Foreign state: every provider that tags reasoning by model drops what it cannot read across
  completed turns (Anthropic drops unreadable blocks silently; OpenAI omits other families).
  Only the in-flight tool exchange fails hard (Anthropic 400, DeepSeek 400). So the kit refuses
  foreign state only after the last user text, and drops it before the backend sees it
  elsewhere, counting the drop on the receipt (as Anthropic's `input_transformations` does).
- Anthropic's prefix check binds a block to the unchanged system, tools and earlier messages:
  the caller's verbatim replay (ruling connector-opaque-state-item) is necessary, and the Claude
  connector's lowering must be deterministic (B4).
- The cheap providers (1d) all keep plaintext `reasoning_content` and want it replayed inside a
  tool loop; the item stays opaque to callers either way.
- Spend (B3b): LiteLLM and OpenRouter both bound a request before the call as estimated input
  plus `max_tokens` times the output price, hold it, and settle to actual; LiteLLM without a
  database fails open, which ruling connector-owner refuses. Anthropic returns tokens only, so
  cost is the connector's arithmetic over a price table it owns. v3 therefore makes
  `max_output_tokens` required, so the bound exists.
